# Google Docs development setup

1. Create a project in [Google Cloud Console](https://console.cloud.google.com/), then enable **Google Docs API** under APIs & Services → Library. No Drive listing or unrestricted Drive scope is used.
2. Under Google Auth Platform configure Branding (app name, support email), Audience (External or your organization's Internal audience), and Data Access. Request `https://www.googleapis.com/auth/drive.file` and `email`. In External **Testing**, add each tester's Google account under Audience → Test users.
3. Create an OAuth client of type **Web application**. Register the exact authorized redirect URI `http://127.0.0.1:3000/api/google/callback`. If using localhost instead, also register `http://localhost:3000/api/google/callback` and change the environment setting to match the browser origin exactly. No JavaScript OAuth client is used.
4. Copy `.env.example` to `.env.local`, fill in the web client ID and secret through secure local settings, and set `GOOGLE_REDIRECT_URI`. Never paste credentials into chat or commit `.env.local`. Start `pnpm dev`, visit `/workspace`, select Google Docs, connect, enter a title, and create a document.
5. In Vercel Project Settings → Environment Variables, set the same three variables for **Preview** using the full stable preview origin, for example `https://your-preview.example/api/google/callback`. Register that exact URI in Google Cloud. Wildcard callback URLs are not supported; changing preview hosts requires registering and configuring the new exact callback. Configure **Production** separately with its canonical HTTPS callback before any future production use. This task does not deploy either environment.
6. Initiate live testing yourself only after configuration. Try a short single draft, pause/resume, then two drafts with the revision strategy you want to inspect. Open the Google Doc; success means the fresh final read reports an exact match. We have not performed live Google API tests during implementation.

## Security and hosting limits

The authorization code flow uses single-use state, S256 PKCE, an exact configured redirect URI, and opaque HttpOnly, SameSite=Lax cookies (Secure on HTTPS; HTTP only for local loopback development). Mutations require an exact Origin, JSON, and a custom request header. Access tokens remain in a bounded, expiring **server memory** vault; no refresh tokens are requested or stored. Connections expire before the access token, at most one hour. Reconnect and reconcile to continue. Disconnect calls Google's revocation endpoint and clears the session; failed revocation is surfaced for retry or manual revocation in Google Account → Third-party connections.

This vault is suitable for a single-process development/demo host. **Vercel multi-instance/serverless routing does not provide shared memory**: authorization callbacks or later requests may land on another instance and require reconnecting. Environment configuration alone does not make durable hosted OAuth sessions work. A shared, encrypted, TTL-limited server-side session/token store is required before reliable hosted/multi-user use; there is no insecure cookie-token fallback. Process restart, instance changes, and access expiry preserve browser recovery data but require reconnecting. No paid auth provider is needed.

Use the same browser origin as the configured callback. Only connect trusted accounts during development. Tokens, upstream error payloads, and document text are never written to server logs. Browser draft/checkpoint storage does contain private text, as before, but never Google credentials. Clearing that storage loses automatic recovery. Disconnecting revokes access; it does not delete the document or saved progress. Expired local sessions cannot revoke an already-discarded token: use Google Account settings if full grant revocation is desired after expiry/restart.

## Synchronization and recovery

`GoogleDocsOutputAdapter` uses a host-supplied transport, `documents.get?includeTabsContent=true`, and ordered atomic `documents.batchUpdate` with `requiredRevisionId`. The engine's already-executed operations are sent at roughly 30-second checkpoints, at stage boundaries, and during final draining. Requests contain bounded chronological groups (up to 180 engine events / 400 API subrequests). There is no keystroke-per-request loop. Quota backlogs drain at controlled spacing. Stage boundaries ensure Draft 1 is confirmed before revision batches. Pauses and stops cancel future scheduling; an in-flight write may still commit. Stopping preserves confirmed Google content and the recoverable local session.

Every remote batch first forces the existing engine checkpoint, persists its exact event IDs, and uses the existing `AdapterExecutor` write-ahead journal with an aggregate before/after range for reconciliation. Individual operations keep `${sessionId}:${eventId}` identities; batch IDs name the event span. Recovery reads Google and compares with journal before/after text: confirmed batches advance once; unapplied batches retry with conditional revision control; unexpected content pauses without overwriting collaborators. Refreshing restores the local engine paused, reconnect Google if needed, select **Resume saved session**, and reconcile before resuming. A timed-out write is never blindly repeated.

Only explicit 429 rejections retry automatically, using bounded exponential backoff, jitter, and Retry-After. 5xx/network timeouts are uncertain and require reconciliation. 400 revision errors, 401 expiry, and 403 permissions errors are shown separately. User/session and project write limits are configurable via the example environment values; these are conservative local guards, not promises about Google's quotas. Multi-instance/project-wide quota enforcement also requires shared infrastructure. Internal cadence, scheduler and adapter limits are constructor options, with no ordinary-user experimental settings.

Local completion is separate from remote completion. Google reports Complete only after all confirmed operations and an exact fresh read against the approved final text, including trailing whitespace and paragraph order. Missing, duplicated, reordered, or changed characters fail that equality check; recovery never silently forces a target over external changes. Real batch timing, outcome, retry count, session/document/batch IDs, and confirmed character count are retained in the bounded browser binding activity log, separately from the full simulation timeline. No Developer Mode dashboard is implemented.

## Supported documents and extension boundary

New plain-text TypeFlow documents are the supported target. New runs require a new empty document; existing results are never cleared automatically. UTF-16 offsets include emoji and paragraph newlines; Google's mandatory terminal newline is excluded from user text. One unambiguous tab is supported and its ID is included in insertion/deletion ranges. Tables, nested/multiple tabs, lists, embedded objects, suggestions, discontinuous ranges, and control/private-use characters that Google strips fail safely. General rich-text or arbitrary existing-document editing is not supported.

Both single and two-text modes use the existing revision/proofreading engine and independent settings. Smart, Minimal, Paragraph Rewrite, Full Rewrite and supported edit strategies retain their original ordered engine operations. Multiple operations in a batch do not imply separate visible Google versions. Google's version-history grouping is controlled by Google; actual automated edits and timestamps do not prove independent human authorship.

A future extension supplies `GoogleTransport` using its own `chrome.identity` authorization, storage/journal ports, and a scheduler implementing the existing `Scheduler`/`ExtensionWakePort` contracts (for example `chrome.alarms`). Website OAuth sessions cannot be reused as extension authentication. Neither the extension nor a background server runner is implemented. The foreground page must remain open; suspended/throttled browsers can delay timing, and no historical writes are fabricated.
